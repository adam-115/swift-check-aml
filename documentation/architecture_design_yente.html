Contexte Architectural & Objectifs de la Refonte

❌ L'Ancien Modèle (Rigide & Fragile)

  • Chemins absolus codés en dur : Présence de constantes comme D:\projects\swiftcheck-aml\... ou D:\test-parser\... dans les plugins. Toute migration d'OS ou de disque provoquait des pannes immédiates.
  • Gestion manuelle de Yente : Chaque mise à jour nécessitait de modifier à la main manifest.yml puis de relancer manuellement le conteneur Docker.
  • Échecs réseaux Uvicorn / HTTP 400 : Négociation HTTP/2 non supportée sur socket cleartext entre le client Java et Uvicorn.
  • Données non dédupliquées : Listes de sanctions (ex: SECO) avec cibles dupliquées et noms fragmentés doublés.

✅ Le Nouveau Modèle (Dynamique & Résilient)

  • Découplage 100% dynamique : Résolution de chemins via ParserConfig.resolveTargetNdjsonFile() gouvernée par la base de données.
  • Auto-enregistrement Yente : Le service YenteManifestService déclare automatiquement les datasets et notifie l'API via /updatez sans coupure de service.
  • Protocole HTTP/1.1 Strict : Élimination complète des anomalies de protocole sur les requêtes Yente.
  • Batching Multi-queries : Traitement par lots (25 cibles) avec un pool de 4 threads, garantissant une exécution ultra-rapide sans surcharger Elasticsearch.

Le Cœur du Découplage : ParserConfig

Pour garantir l'absence totale de chemin en dur sur le système de fichiers, l'objet ParserConfig implémente une résolution en cascade sécurisée. Le code du plugin ne manipule plus jamais de chaîne absolue :

package com.swiftcheck.aml.config; import java.io.File; import lombok.Data; @Data public class ParserConfig { private long id; private String name; private String outputUrl; private String datasetName; private String yenteDataFolder; // Récupéré depuis ApplicationConfigEntity en base private String yenteUrl; // ex: http://localhost:8000 private String yenteManifestPath; // Emplacement de manifest.yml /** * Résout dynamiquement le fichier .ndjson cible sans aucune dépendance à une lettre de lecteur */ public File resolveTargetNdjsonFile(String subfolder, String filename) { // 1. Priorité au dossier configuré globalement par l'administrateur dans l'IHM String base = (yenteDataFolder != null && !yenteDataFolder.trim().isEmpty()) ? yenteDataFolder : outputUrl; // 2. Repli de secours sur le répertoire courant du projet if (base == null || base.trim().isEmpty()) { base = "."; } // 3. Construction et création transparente des dossiers manquants File dir = (subfolder != null && !subfolder.trim().isEmpty()) ? new File(base, subfolder) : new File(base); if (!dir.exists()) { dir.mkdirs(); } return new File(dir, filename); } }
Gain Majeur : Si le serveur est migré sur Linux (ex: /mnt/sanctions-data) ou si un volume Docker est monté, il suffit de modifier le champ dans les paramètres de l'application. Aucun des 25 plugins n'a besoin d'être recompilé ni modifié.

Le Pont d'Intégration Yente : YenteManifestService

La classe YenteManifestService automatise la publication des sources de données dans le catalogue Yente et synchronise Elasticsearch en temps réel.

Séquence d'Exécution & Rechargement à Chaud

  1. Déclenchement du parsing : L'utilisateur ou un cron appelle POST /api/ftm/parsers/execute avec l'ID du parser.
  2. Génération du flux FTM : Le plugin extrait la source officielle et génère le fichier .ndjson normalisé dans le sous-dossier résolu.
  3. Vérification du Manifeste : YenteManifestService.addDatasetToManifest(parser) charge le fichier manifest.yml défini en base.
  4. Mise à jour du Catalogue :
    • L'entrée du dataset est ajoutée sous la clé racine datasets: avec son chemin relatif conteneur (ex: /data/ACPR-France/acpr_sanctions_ftm.ndjson).
    • Le dataset est automatiquement rattaché dans la liste children: du catalogue global name: default.
  5. Signal de Rechargement Yente : Le service émet une requête HTTP POST http://localhost:8000/updatez?token=adam.
  6. Indexation Elasticsearch : Yente relit le manifeste, charge les nouveaux enregistrements et met à jour ses index sans interruption de service.

Protocole de Test & Résilience des Plugins

🌐 HTTP/1.1 Obligatoire

L'ancien client Java tentait une négociation HTTP/2 via l'en-tête Upgrade: h2c. Uvicorn rejetait la connexion avec un code HTTP 400. En imposant HttpClient.Version.HTTP_1_1, 100% des requêtes vers Yente sont stables.

📦 Batching Multi-queries

Les listes volumineuses (19 321 entités OFAC, 8 667 entités SECO, 6 578 entités DG-Trésor) sont partitionnées en lots de 25 cibles sous la structure Yente {"queries": {"q0": {...}, "q1": {...}}}.

🧵 Pool de 4 Threads

L'exécution concurrente est bridée à un pool fixe de 4 threads. Cela offre le débit optimal (~20 entités/seconde) tout en évitant les surcharges de mémoire ou les pics CPU d'Elasticsearch.

Diagramme de Séquence : Protocole de Test d'Intégration & Criblage en Masse (Lots de 25)

Cas d'École : Déduplication & Nettoyage du XML SECO Suisse

Le registre officiel SECO Suisse présentait deux anomalies critiques dans son XML source :

  • Redondance des entités : Chaque individu apparaissait jusqu'à 4 fois (une occurrence par régime de sanction ou amendement), gonflant artificiellement la liste à 17 312 cibles.
  • Doublage textuel des noms : La lecture simultanée des balises <name-part> et <value> doublait chaque mot (ex: "Mayu Mayu Jibril Jibril...").

Solution appliquée dans SecoSanctionsParserService.java : Déduplication stricte via un Set<String> seenIds basé sur le numéro ssid et lecture exclusive de <value> avec réinitialisation du buffer. Le registre a été ramené à 8 667 entités parfaitement assainies, atteignant 99,86% de succès lors du test de criblage.
